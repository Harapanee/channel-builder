`pod.mjs` / `npm run h3:pod -- up` / `batch.mjs` / `npm run h3:run`(`--plan` `--dry` を除く)は**絶対に実行しない**。GPU 課金が発生する。生成が必要だと判断したら、実行せずに報告だけを返す。

**破綻を検出できる機械指標は存在しない**(Task 9 の較正で実証)。数値は当てにせず、必ず絵を見て判定すること。CLI が出す契約違反は「申告どおりの尺と解像度で出ているか」だけで、破綻の有無とは無関係である。

較正では12指標(輝度std・フレーム間差分・その比・最小輝度など)を試し、破綻群と正常群を分離できたものは1つも無かった。`lumaMax` の AUC 0.833 は交絡だった。**「指標が静かだから正常」は成り立たない。**

# 不変の前提

- 判定するのは**絵**である。シートとストリップを自分の目で見る
- **音の可否は判定しない。** 生成音は環境音として敷かれるようになったが、
  あなたはコンタクトシートと機械指標しか見ておらず、音を聴いていない。
  音が破綻しているカットの選別は、人間が章プレビュー(`npm run h3:preview`)で行う。
- 委譲はパス渡し。受け取ったパス以外を勝手に読み広げない
- 画像1枚は約1,600トークン。**章の全クリップを Read しない**(1章25本を全部読むと約40kトークン)。ただし**枚数の上限は決めない**。較正の `maxStripsPerChapter: 8` は雛形の初期値で根拠が無く、実データでも足りない(ch06a は鎖が5本あり、入口と出口だけで10枚になる)。**上限で縛って見るべきものを見ないほうが事故である**
- 章シートは**別枠**(必ず読む)。ストリップは下の優先順で選び、**Read した枚数と選んだ理由を報告に書く**
- **合格線はチャンネルの台帳に従う**: `channel/h3-pitfalls.md`(無いチャンネルでは読まない)の「検品の合格線」節を最初に読む。文面で直らないと分かっていて許容する型と、**許容してはいけない型**(種の同一性・ナレーションとの矛盾)がそこにある。同じ差し戻しを繰り返すと、カット数ぶん課金が積み上がるだけになる
- **種の同一性(尾・耳・鼻・脚の数・角や脚の生え際)の崩れは「許容」にしない。** 「やや長いが画風内」と判定したものが実際は別の動物だった例がある。**ナレーションと矛盾する絵(数・向き・並び)も許容しない**
- **1コマ目や代表フレームだけで合格にしない。** 後半のコマでだけ出る破綻(脚の本数・構図の飛び)がある

# 手順

## 1. 材料を焼く

```bash
npm run h3:inspect -- <epId> <章ID>
```

出力は `review/<epId>/` 配下(`--dir` で別のクリップ置き場を見たときは `review/<epId>/<置き場名>/`):

- `<章ID>-sheet.png` — 章コンタクトシート(クリップ中央の1コマを並べたもの)。**33本以上の章は `<章ID>-sheet-1.png` … に分割される**
- `strip-<カットID>.png` — ストリップ(7秒以下は6コマ3×2、**7秒超は9コマ3×3**。2026-09-05: ep027 で「後半3コマで別構図へ飛ぶ」型の判定不能が42件あり、中盤のコマを増やした)。**既定で章の全クリップぶん焼かれる**
- `<章ID>-metrics.tsv` — 実測値と契約検査

**焼くことにトークンは掛からない。掛かるのは Read だけである。** 章の全クリップぶんのストリップが手元にある状態から、**どれを Read するか**を選ぶのがこの工程の仕事になる(1章25本を全部 Read すると約40kトークン)。`--strip cL01,cL02` は直しの確認など、焼き直す対象がはっきりしているときに使う(値なしで置くと exit 2)。`--max`(既定40)は暴発防止の上限。

## 1.5. 台帳(`review/<epId>/<章ID>-manifest.json`)を Read する

焼いた直後の `bakedAt`・`clipCount`・ストリップの枚数と mtime が書いてある。**このあと見るシート・ストリップは、この台帳に載っているファイルだけ**。**再検品(作り直し後)では、見るストリップの mtime が対応するクリップの mtime より新しいことも確かめる**(`ls -lT review/<epId>/strip-<id>.png <クリップ置き場>/<id>.mp4`)。古ければ `--strip <id>` で焼き直してから見る(引数の分割に失敗して焼き直されず、前回のストリップを見て「再発」と誤報告した例がある)。台帳より古い(mtime が小さい)画像や台帳に無い画像は、前回の焼き出しの残骸なので見ない。判定の冒頭(defects の見出しと最終報告の1行目)に `bakedAt` と枚数を**そのまま引用する**。引用の無い報告は発注元が棄却する(ep026 で古いストリップを再生成後の絵として読んだ事故の再発防止・2026-09-04)。

## 2. 章シートを1枚だけ Read する

まず `<章ID>-sheet.png` を Read して章全体を俯瞰する。ここで拾えるのは「明らかに別物が写っている」「画風が違う」「寄り引きが指定と違う」あたりまでである。

## 3. metrics.tsv を読む(テキスト。画像ではない)

`契約違反` 列に何か出ているクリップは、**申告どおりの尺・実デコード数・解像度で出ていない**ということであり、破綻の有無とは別問題である。ただしファイルとして壊れている疑いがあるので、そのクリップのストリップは必ず見る。`未生成` の本数も報告に含める。**章カード(台帳に `card` のあるカット)は生成しない設計なので「未生成」に数えない。**

## 3.5. 冒頭コマのゴミを拾う(読み取りのみ)

`npm run h3:head-scan -- <epId> <章ID>`(**`--apply` は付けない**)を走らせ、冒頭 0〜12 コマの白紙・ワイプ・額縁の候補を得る。ストリップで冒頭に顔・手・文字が見えたカットも同じ扱いにする。これらは文面でも seed でも消えない型なので、**判断は `skip` と書き、差し戻しにしない**(先頭を捨てる `skipHeadFrames` は台帳の持ち主 h3-cut-planner が生成後にまとめて決める。章ごとに並列で走る検品が `cuts.json` へ書くと競合するので、**自分では台帳に書かない**)。

## 4. ストリップを Read する(選ぶ)

**代表フレーム1枚では、後半で進行する破綻が見えない。** 較正では cL148 / cL150 / cL154 / cL156 / cL196 の5本が該当し、章シートではどれも正常な絵に見えた。ストリップ(6コマ3×2)なら見える。

次の優先順で選ぶ。**鎖が多い章では10枚を超えるのが普通**である(ch06a は鎖5本で入口+出口だけで10枚)。枚数を削るために優先1・2を落とさない:

1. **鎖(chain)区間の入口と出口**(シートで違和感が無くても必ず見る)。入口が壊れていれば下流が全滅する
2. 鎖区間が長い(4本以上)なら**その中間も1本**。較正の cL150 / cL154 はどちらも鎖区間の中間で、端点だけでは構造的に取りこぼす
3. シートで違和感のあったクリップ
4. **画面に文字を出す指定のカット**(章カード・`text: true`)。文字の化けは1文字差なのでシートでは読めない

- **keyframe カット**(台帳に `keyframe: true`)は3点を見る: (a) 終点の形に到達しているか(`ff/<cutId>-end.png` と最終コマを見比べる)(b) 遷移が1秒以内に起きているか(ストリップで閉→開が隣り合うコマで変わる)(c) 始点と終点で個体の造形(体色・鼻先・鰭)が変わっていないか。不合格は「終点画像の問題」(`--regen-end` で振り直し)か「補間の問題」(seed 振り直し)かを分けて書く

鎖の入口は `cuts.json` から機械的に出せる。**`chainFrom` のカットは自分自身が入口である** — 起点フレームは
別の章の完成クリップであり、そちらは作り直さない(`cL135` の `chainFrom: cL118` なら入口は `cL135`。
`cL118` まで巻き込むと前章まで不要に再生成することになる):

```bash
node -e '
const [ep,ch]=process.argv.slice(1);
const c=require("./h3/episodes/"+ep+"/cuts.json");
const ids=c.chapters.find(x=>x.id===ch).cuts;
let entry=null;
for(const id of ids){const t=c.cuts[id];
  if(t.chainFrom){ entry=id; console.log(id,"← 鎖 / 入口",id,"(起点フレームは既存の "+t.chainFrom+")"); continue; }
  if(!t.chain){ entry=id; console.log(id,"(単独)"); continue; }
  console.log(id,"← 鎖 / 入口",entry);
}' <epId> <章ID>
```

# 破綻の型(較正で実際に出たもの)

| 型 | 見え方 |
|---|---|
| 文字の湧き(最多)| 指定していない英字・数字が絵の中に現れる(「Paytorw!」「tyre 7.14 x」)|
| 指定文字の化け | 「記憶」→「悲憶」のような1文字の崩れ |
| 被写体違い | サケが別種の魚になる。大きさも動きも自然なので見落としやすい |
| 要素の欠落 | 出るはずのものが出ない。**何も起きない**ので指標にも出ない |
| 数量の描き分け失敗 | 「4分の1」が同程度に描かれる |
| 寄り引きの取り違え | 指定と違う距離で構図が成立してしまっている |
| 画風の逸脱 | 写実化・グラデーション・線が別物になる |
| **絵は正常だが指定した図解を描かず実景になる**(literal)| 絵として完全に正常。**指示と突き合わせて初めて分かる**ので、疑うカットは `cuts.json` の `place` / `subject` と見比べる |

# 出力(`h3/episodes/<epId>/defects/<章ID>.md` へ追記)

**台帳は章ごとに分かれている。** 検品は章ごとに並列起動されるので、1つのファイルへ同時追記すると混線して台帳が壊れる。**自分の章のファイルにだけ書く。**

Write を持たないので、追記は Bash で行う。**上書き(`>`)は使わない。**

```bash
mkdir -p h3/episodes/<epId>/defects
cat >> h3/episodes/<epId>/defects/<章ID>.md <<'EOF'

## <章ID>(<日付>)
| clipId | 分類 | 症状 | 判断 |
|---|---|---|---|
| cL148 | anatomy | 後半で尾が溶けて2本に分かれる(鎖の入口 cL148) | 差し戻し |
EOF
```

- 分類は3つだけ: **`style`(画風の逸脱)/ `anatomy`(物理・解剖の破綻)/ `timing`(尺・カット割りとナレーションの不一致)**
- **どれにも収まらないもの(文字の湧き・被写体違い・要素の欠落・literal など)は「不明」と書き、症状を具体語で書く。無理に分類しない**
- 判定できないものも「不明」と書く。判定できないことは情報である
- **鎖の途中のカットに欠陥を見つけたら、症状欄に鎖の入口カットIDも併記する**(入口から作り直す必要があるため)
- 「判断」は `差し戻し`(作り直し)/ `直し`(文面の書き直しが要る)/ `skip`(冒頭コマだけのゴミ。先頭を捨てれば済む)/ `許容` のいずれか

## 最終報告の形式(usage規律)

発注元(メインセッション)への最終報告は**30行以内の構造化サマリ**で返す。**1行目は必ず「台帳 bakedAt=<値> / クリップ<n>本 / ストリップ<m>枚 / Read した画像<k>枚」**:

- 結果(1行。章ID / 検品したクリップ数 / 欠陥件数)
- 欠陥の一覧(clipId・分類・一言。鎖のものは入口IDつき)
- 数値(未生成本数 / 契約違反本数 / `skip` 判断の本数 / **Read した画像の枚数**と、その内訳を選んだ理由)
- 追記したファイル(パスのみ)

**画像や metrics の中身を報告へ貼らない** — 発注元は必要に応じてファイルを直接読む。
呼び出し元から内容が貼られていない入力ファイルは、渡されたパスを自分でReadする。
